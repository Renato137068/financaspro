Perguntas que a Play Console não faz — e as respostas do seu código

1. Se o manifesto diz “sem cadastro”, o APK abre sem pedir login?
Não. config.js embute SUPABASE_URL e SUPABASE_ANON_KEY. Com isso, SUPA_AUTH.isActive() é verdadeiro e authController.js abre o overlay de login no boot — mesmo sem o usuário ter escolhido nuvem. O mesmo texto aparece em manifest.json, meta do index.html e privacidade.html (“dados não são enviados a servidores” no modo padrão).
Resposta honesta: 38/100
2. O PIN de 4 dígitos protege os dados financeiros contra alguém com o celular desbloqueado?
Não de forma criptográfica. O PIN só oculta a UI via classe pin-locked em critical-inline.css. Transações continuam em localStorage/IndexedDB em JSON legível. Com criptografia local ativa, pin-guard.js ainda lê fp-config cru e pode falhar o parse do blob enc3:.
Segurança efetiva: 45/100
3. Biometria guarda a sessão só no Keystore?
Não exclusivamente. auth-biometric.js guarda refresh token no Keystore, mas o cliente Supabase persiste sessão completa em localStorage (fp-supabase-auth). XSS ou extração do WebView ainda expõe tokens. Ao sair (_executarLogout), AUTH_BIOMETRIC.disable() não é chamado — credenciais biométricas podem reabrir sessão após logout.
Custódia de sessão: 52/100
4. “Criptografados na nuvem” no rodapé do login é sempre verdade?
Não para todos. O texto fixo em index.html aparece antes de qualquer login. Criptografia local é opt-in e a passphrase real não tem UI — só chave de dispositivo ao lado do ciphertext em local-crypto.js. Usuário local puro nunca “criptografou na nuvem”.
Copy vs realidade: 40/100
5. O indicador “Salvo no servidor” só aparece para quem está logado na nuvem?
Não necessariamente. sync-indicator.js usa DADOS._nuvemAtiva() (presença de chaves Supabase), não isCloudUser() (sessão ativa). Com build padrão, estados de nuvem podem aparecer sem conta.
Feedback de sync: 58/100
6. Excluir conta apaga tudo que o usuário imagina?
Só a cópia na nuvem. Fluxo documentado em init-navigation.js — dados locais permanecem até “Apagar todos os dados”. No path Supabase, exclusão não exige reautenticação (senha/biometria), diferente do path Express que usa window.prompt.
Direito ao esquecimento: 72/100
7. O app funciona 100% offline na primeira abertura?
Parcialmente. Service worker com precache e fontes locais — bom. Mas OCR Tesseract vem do jsDelivr na primeira vez; com Supabase embutido, login bloqueia uso sem rede na abertura. Recorrentes materializam localmente (lifecycle.js) — ponto positivo frequentemente ignorado.
Offline real: 68/100
8. Há dark patterns de assinatura?
Não encontrados. Sem countdown falso, confirmshaming ou botão de cancelar escondido. Paywall fecha com Escape. Quotas só na nuvem; local é ilimitado — assimétrico mas declarado em billing.js. Risco maior é dual billing (Play + Stripe) sem onboarding claro de “onde assinei”.
Ética de monetização: 78/100

Achados críticos e incomuns (com evidência)

P0 Promessa “local-first” vs binário cloud-first

Três superfícies públicas prometem ausência de cadastro e de envio de dados; o build de produção já carrega Supabase e força tela de login.

  • manifest.json — “sem cadastro… sem internet”
  • privacidade.html §1 — modo padrão não envia a servidores
  • js/core/config.js — URL e anon key hardcoded
  • js/authController.js — overlay no boot quando Supabase ativo

P0 PIN como cortina, não como cofre

Auditorias de loja raramente abrem DevTools. Aqui, pin.js + CSS só impedem ver saldos; não há bloqueio de leitura de storage. Para app financeiro, isso deve estar explícito na ficha e na UI do PIN.

P1 Criptografia local com buracos

  • Grandes volumes migram para IndexedDB (dados.js → IDB_KV) sem LOCAL_CRYPTO
  • Anexos/recibos em anexos.js — blobs sem cifra
  • Export JSON em init-config.js — plaintext completo (correto para portabilidade, arriscado se compartilhado)

P1 Sessão e biometria — ciclo de vida incompleto

  • Logout não chama AUTH_BIOMETRIC.disable()
  • 2FA/TOTP desativado no path Supabase (supabase.js stub; init-2fa.js exige API Express)
  • Metadados PIN (pinAtivo, tentativas) podem subir na sync — hash não sobe, mas vaza hábito de segurança

P1 Versões divergentes na mesma instalação

Usuário/suporte podem reportar bugs na versão errada:

  • Gradle / package.json: 11.3.4
  • config.js: 11.3.0
  • Rodapé Perfil: v11.0.0

P1 Superfície WebView / CSP

  • style-src 'unsafe-inline' no meta CSP
  • connect-src inclui localhost:4000 no bundle de produção
  • SW precacheia config.js (chaves), supabase.js, pin.js
  • Tesseract sem SRI (reconhecido no comentário do HTML)

P1 Android — endurecimento incomum

  • minifyEnabled false — JS/Java legível no APK
  • file_paths.xml — external-path path="." amplo demais
  • Sem FLAG_SECURE — saldos e tela de PIN em screenshot/recents
  • Positivo: só INTERNET, cleartext off, backup off

P2 Coerência de produto / código morto

  • onboarding.js — _mostrarConvite() definida, nunca chamada
  • Três sistemas de onboarding (dashboard, setup-guide, tour inativo)
  • Exportação cloud via API existe no backend; UI só exporta JSON local
  • Sync pull sem paginação — risco de OOM em contas grandes

Pontos que poucos apps fazem bem

  • RLS Supabase + testes pgTAP de isolamento entre usuários
  • Sync com detecção de conflito e outbox (não é “último write wins” cego)
  • Telemetria opt-in; sem Firebase/Analytics embutido
  • Backend Express: refresh hasheado, CSRF, lockout, TOTP cifrado em prod
  • Sem confirmshaming; tour não bloqueia; quota banner só quando relevante
  • Charts com tabelas SR (chart-a11y.test.js)
  • Correções recentes: overlay auth esconde header; biometria na etapa senha; banner vazio removido

Plano de correção priorizado

Fase 1 — Antes de subir na Play (bloqueadores de confiança)

Impacto: evita rejeição por engano do usuário e inconsistência Data Safety.

  1. Build “piloto local”: SUPABASE_URL e SUPABASE_ANON_KEY vazios no release, OU atualizar manifest, privacidade, ficha e Data Safety para cenário CLOUD.
  2. Alinhar versão em Gradle, config.js, rodapé Perfil e changelog.
  3. Reescrever rodapé auth: separar copy local vs nuvem; não prometer criptografia inexistente.
  4. Chamar AUTH_BIOMETRIC.disable() no logout e na exclusão de conta.

Fase 2 — Segurança que o usuário acredita ter

  1. UI do PIN: “Oculta saldos neste aparelho — não criptografa dados contra acesso técnico”.
  2. Estender cifra a IDB + anexos OU remover toggle que sugere proteção total.
  3. pin-guard.js usar camada de storage cifrada.
  4. FLAG_SECURE em auth, PIN e saldos.
  5. Reauth antes de deleteAccount no Supabase.

Fase 3 — Polimento de produto maduro

  1. Sync indicator: usar isCloudUser() + sessão válida.
  2. Paginação no pull Supabase; export cloud na UI do Perfil.
  3. R8/minify release; estreitar file_paths.xml.
  4. Remover localhost do CSP no build prod; SRI no Tesseract.
  5. Supabase MFA ou documentar ausência na privacidade.
