Motor excelente, vitrine quebrada A lógica por trás do orçamento é das melhores do app (aritmética em centavos, projeção honesta com teto diário, insights acionáveis). Mas o bloco mais visível da tela — o Header Estratégico — está congelado em zero: nenhum JS o preenche. O usuário vê “Total planejado R$ 0,00” no topo enquanto os cartões logo abaixo mostram R$ 2.400 gastos. Além disso há HTML e código mortos.

! Achado crítico (funcional)

Verificado no navegador: renda R$ 5.000 e R$ 2.800 em despesas lançadas.

P0 · Header estratégico morto

O topo do orçamento nunca é preenchido — mostra zeros mesmo com dados reais

Os 7 elementos do “Header Estratégico” (#orc-saldo-disponivel, #orc-percent-restante, #orc-tendencia, #orc-total-planejado, #orc-total-realizado, #orc-categorias-criticas, #orc-economia-mes) não são atualizados por nenhum JS — buscas em todo o código dão zero referências. Eles ficam no placeholder do HTML para sempre.

Por que é grave. Não é só cosmético: para um app de orçamento, o KPI de topo mostrar sempre zero enquanto os cartões de baixo mostram gasto real é uma contradição que destrói a confiança no número. Os cartões 50/30/20 funcionam (o teste confirmou Necessidades R$ 2.400 de R$ 2.500) — a lógica existe, só não está ligada ao header.

2 HTML e código mortos (a tela promete o que o JS não entrega)

P1 · Inconsistência HTML ↔ JS

Categorias agrupadas e histórico existem no HTML mas nunca são usados

Grupos de categoria. O HTML define “Categorias Críticas / Requer Atenção / Saudáveis” (#orc-group-critical/attention/healthy com contadores e empty state). Mas renderCategorias sobrescreve todo o #orc-categorias com uma lista plana (.orc-cat-item) — os grupos nunca aparecem. Confirmado em runtime: #orc-critical-list fica vazio; o container só tem itens planos.

Histórico. renderHistorico roda a cada render mas mira #orc-historico, que não existe no HTML — retorna na hora, sem efeito. Código morto.

Região viva órfã. #orc-live-region (aria-live) existe no HTML mas nada escreve nela — as mudanças de orçamento não são anunciadas a leitores de tela.

Onde init-orcamento.js:325-352 (renderCategorias), :354-382 (renderHistorico)
Correção decidir: implementar o agrupamento/histórico OU remover o HTML/JS morto; ligar o live-region aos updates

6 O que já está bom (manter)

  • Motor financeiro exemplar — orcamento.js soma em centavos inteiros (sem drift de float), com comentários explicando o porquê.
  • Projeção honesta — projetarCategoria espera até o dia 3 para não dar alarme falso, é linear de propósito e devolve um teto diário sugerido (“R$ 10/dia” em vez de “segure os gastos”).
  • Insights acionáveis — estouro por grupo e por categoria, meta de poupança, maior gasto, projeção do mês; some quando não há nada útil a dizer (não vira ruído).
  • Cartões 50/30/20 funcionam — gasto/limite/percentual/estado corretos (confirmado em runtime).
  • Contraste OK nos dois temas — passa AA no claro e no escuro (14–16:1); sem o bug de tema das abas Resumo/Lançamentos/Extrato.
  • Regra 50/30/20 personalizável com validação de soma = 100% e feedback ao vivo do total.
  • Robustez — renderDashboard em try/catch; categoriasEmRisco isolado para não derrubar a aba.
  • escapeHtml nos rótulos de categoria da lista e nas mensagens de risco.

7 Metodologia & conceitos aplicados

  • Correção funcional / wiring: conferência de que cada elemento da tela é realmente alimentado pelo JS (busca de referências + teste em runtime com dados semeados).
  • Consistência HTML↔JS: HTML que promete estrutura que o JS ignora ou sobrescreve; código morto.
  • Correção financeira: aritmética em centavos, projeção, classificação 50/30/20.
  • Acessibilidade: WCAG 2.1 — contraste (1.4.3), progressbar (4.1.2), região viva (4.1.3).
  • Contraste medido: getComputedStyle + razão WCAG em claro e escuro, estado estável.
  • Segurança de front-end: XSS via innerHTML (ponto não escapado).
  • Manutenibilidade: estilos inline, código morto, subutilização do data layer.
