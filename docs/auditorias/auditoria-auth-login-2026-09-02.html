Veredito: fluxo ambicioso, execução instável

A base (login em 2 etapas, Supabase, biometria nativa, focus trap, mensagens traduzidas) é sólida. Porém há dois backends de auth concorrentes (Express vs Supabase), bugs de camada visual já corrigidos parcialmente, e lacunas que explicam “digito senha e não entra”, biometria confusa e cadastro que parece funcionar mas trava.

Sintoma que você reportou: “Coloco e-mail e senha e não entra.”
Causa raiz identificada (já corrigida no repositório, exige novo AAB): após login bem-sucedido, o diálogo “Deseja usar biometria?” abria com z-index 500, atrás do overlay de login (900+). A promise só resolvia ao fechar o modal — invisível — então o app parecia travado. Fix: fechar overlay antes de oferecer biometria (authController.js ~L210) + modal acima do overlay (modals.css).

Catálogo de achados (prioridade)

P0 Logout não revoga biometria

_executarLogout() chama DADOS.encerrarSessao() mas nunca AUTH_BIOMETRIC.disable(). Quem sair da conta ainda pode reentrar via impressão digital com token antigo no Keystore até expirar no servidor.

P0 Dois backends de auth no mesmo app

Express (dados.js → /api/v1/auth/*, cookies HttpOnly, TOTP real) vs Supabase (supabase.js sobrescreve loginApi, stub TOTP). O APK usa Supabase hardcoded em config.js. Código morto do path Express confunde manutenção e testes E2E não cobrem Supabase.

P1 2FA (TOTP) inexistente no fluxo Supabase

DADOS.verifyTotpLoginApi = () => Promise.resolve() em supabase.js L191. UI de TOTP em index.html e init-2fa.js exige DADOS._apiAtiva() — falso com Supabase. Usuário cloud não tem 2FA apesar da tela existir no Perfil como “Requer login na nuvem”.

P1 Política de senha inconsistente

  • Frontend cadastro: mín. 8 + número/especial (password-policy.js)
  • Supabase aceita 6 caracteres — mensagem em supabase.js L73 contradiz o hint do formulário
  • Login não valida complexidade (correto), mas cadastro via API Supabase pode passar senha mais fraca se validação client falhar

P1 Sessão dupla: localStorage + Keystore

Supabase persiste sessão em fp-supabase-auth (localStorage WebView). Biometria guarda refresh token no Keystore. São caminhos paralelos — logout limpa um, não necessariamente o outro.

P1 Desbloqueio obrigatório a cada abertura

_authDesbloqueadoNestaCarga começa false. Mesmo com sessão Supabase válida, toda abertura exige senha/biometria. Estilo banco — correto para segurança, frustrante se não comunicado. Ao voltar do background, visibilitychange revoga de novo.

P1 Recuperação de senha no Capacitor

resetPasswordForEmail usa redirectTo: window.location.origin. No WebView Capacitor o origin é https://app.financaspro.com (sintético) — link do e-mail pode não reabrir o app corretamente.

P1 Copy enganoso no rodapé do login

auth-footer-note: “Seus dados ficam no seu aparelho e são criptografados na nuvem.” — nem todo usuário ativou criptografia local; nuvem não criptografa automaticamente o JSON financeiro da forma que o texto sugere.

P1 Etapa e-mail não verifica conta

“Continuar” só troca para senha sem ping ao servidor. Usuário descobre e-mail errado ou inexistente só ao submeter senha — mais uma rodada de frustração.

P2 Fluxo TOTP pós-login incompleto

Se Express API exigir TOTP, totpForm sucesso não chama _authOnSuccess completo (falta offer biometria, INIT_CONFIG.aplicarVisibilidadeNuvem).

P2 HTML do overlay desorganizado

#auth-totp-form e #auth-register-form ficam fora de #auth-login-flow mas dentro de .auth-card — tabs ARIA apontam painéis com estrutura inconsistente.

P2 Exclusão de conta sem reautenticação

Path Supabase: duplo confirm no modal, sem senha/biometria. Path Express: window.prompt para senha (má UX, mas mais seguro).

Pontos positivos

  • Login em 2 etapas com saudação, e-mail mascarado, “Usar outro e-mail”
  • Mensagens Supabase traduzidas (_msg): rede, credenciais, e-mail não confirmado, rate limit
  • Focus trap, tabs com teclado, toggle mostrar senha, aria-live nos erros
  • Biometria: rotação de refresh token no TOKEN_REFRESHED
  • Guards anti-loop biometria (_authBiometricInFlight, _authBiometricAutoTried)
  • Overlay esconde header/nav durante login (body.auth-overlay-open)
  • Cadastro valida senha com VALIDATIONS.validarSenha antes de enviar

Plano de correção (ordem recomendada)

Fase 1 — Estabilizar login (1–2 dias)

  1. Gerar AAB com fix modal/z-index já no código (vc28+).
  2. Chamar AUTH_BIOMETRIC.disable() em _executarLogout e exclusão de conta.
  3. Adicionar spinner/“Entrando…” visível no botão durante loginApi.
  4. Toast explícito quando e-mail não confirmado + link “Reenviar confirmação” (se Supabase permitir).

Fase 2 — Clareza para o usuário (2–3 dias)

  1. Reescrever auth-footer-note (local vs nuvem).
  2. Mostrar botão biometria com texto “Configure após entrar com senha” quando disponível mas desativado.
  3. Comunicar na 1ª abertura: “Por segurança, confirme sua identidade”.
  4. Fix redirect recuperação senha para deep link Android (intent:// ou URL real do app).

Fase 3 — Arquitetura (1 semana)

  1. Escolher UM backend auth para o APK (recomendado: Supabase only) e remover stubs Express do path mobile.
  2. Supabase MFA ou remover card 2FA do Perfil quando Supabase ativo.
  3. E2E Playwright contra Supabase (login, cadastro, email confirm mock).
  4. Teste instrumentado Android: biometria enable → logout → não deve reentrar.
