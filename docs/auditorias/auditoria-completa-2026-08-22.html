Prioridade 1 — resolver antes de qualquer coisa nova

P1 · resolvidoNenhuma compressão HTTP em produção

backend/app.js · Dockerfile · docker-compose.yml

app.use(express.static(STATIC_ROOT, …)) serve o build sem nenhum middleware de compressão, e não há compression, nginx ou Caddy em nenhum lugar do caminho. Cada primeira visita baixa app.bundle.js com 460 KB crus quando 117 KB bastariam, e o CSS com 252 KB quando 37 KB bastariam.

Confirmei inspecionando os headers de todas as 13 respostas do boot: nenhuma traz Content-Encoding. Depois subi o mesmo dist/ atrás de compression() e medi de novo, mesmo navegador, mesma emulação:

Métrica (mobile, CPU 4×, ~1,6 Mbps)HojeCom gzipGanho
Bytes transferidos829 KB272 KB−67%
First Contentful Paint3,26 s1,25 s−62%
Largest Contentful Paint5,13 s2,18 s−57%
Load completo5,11 s2,13 s−58%
Correção: npm i compression e, em app.js, antes do express.static: 
import compression from 'compression';
app.use(compression());
Melhor ainda: gerar .br/.gz no build (vite-plugin-compression) e servir pré-comprimido, evitando custo de CPU por requisição. E acrescente ao check-bundle-budget.cjs uma coluna de bytes comprimidos — é o número que o usuário sente, e hoje a esteira não olha para ele.
Como ficou: Ligado compression() antes de rotas e estáticos. Três testes em routes.http.test.js prendem o comportamento — inclusive o de que resposta pequena NÃO é comprimida, para que a escolha fique documentada. Novo teto de precache comprimido no check-bundle-budget: 347 KB de 400 KB.

P1 · resolvidoA esteira de qualidade está vermelha nesta branch

scripts/check-css-tokens.cjs · npm audit · jest coverageThreshold

Rodei os mesmos comandos que o CI roda. Três falham agora:

  • npm run check:css → "a dívida cresceu: 349 contra teto de 348". Um valor literal a mais derruba o passo.
  • npm audit --audit-level=high → 1 vulnerabilidade high em brace-expansion (DoS), apesar do overrides fixando 5.0.8 — o override não alcança a árvore inteira.
  • npm run test:coverage → 8 pisos não atingidos: sync-merge.js (66,3% vs 95%), utils.js, store.js, validations.js, billing.service.js e transaction.repository.js (72,3% vs 90%).

Como a CI só dispara em main/master e PRs para elas, e há 254 arquivos sem commit numa branch de feature, esse vermelho está fora do radar. É o pior lugar para um problema estar: existente e invisível.

Correção: subir o teto de CSS com justificativa no commit ou tokenizar o literal novo; atualizar a árvore para matar o brace-expansion; e — o mais importante — cobrir sync-merge.js, que é o guardião contra perda de lançamento. Depois, ligar a CI também em push nas branches feat/**, para o vermelho aparecer no dia em que nasce.
Como ficou: CSS: token --color-border-print substituiu os dois literais de impressão. Auditoria: brace-expansion para 5.0.9, zero vulnerabilidades. Cobertura: os oito pisos passaram — sync-merge a 100%, e testes novos em transaction.repository, billing.service, store, utils e validations.

P1 · resolvidoFalha de precache do service worker é engolida em silêncio

sw.js — install

cache.addAll(urlsParaCache).catch(() => {}). addAll é atômico: se uma das 144 URLs devolver 404, a operação inteira rejeita e o catch vazio marca o install como bem-sucedido. Resultado: um service worker ativo, o usuário acreditando que o app funciona offline, e nada no cache. Num app financeiro cujo contrato é "sempre funciona", esse é o modo de falha mais caro possível.

Correção: trocar por Promise.allSettled item a item, registrar as URLs que falharam via OBS e só então resolver o install — ou deixar o install falhar de propósito. Falhar alto é melhor que mentir baixo.
Como ficou: Trocado por Promise.allSettled por item, com log do que falhou e install abortado só se nada entrar no cache. O gerador agora também remove do precache qualquer URL sem arquivo correspondente.

Prioridade 2 — próxima janela de trabalho

P2 · resolvidoA cifragem local at-rest guarda a chave ao lado do cofre

js/utilities/local-crypto.js

O material de chave (financaspro_ckey_dev, 32 bytes aleatórios) fica no mesmo localStorage que ele protege, em texto claro. Quem lê o storage — um XSS, uma extensão, uma perícia no perfil do navegador — lê a chave junto. O cryptoPassphrase do usuário teria prioridade, mas vem de DADOS.getConfig(), ou seja, do próprio storage. Além disso, o PBKDF2 usa 100.000 iterações enquanto o backend usa 600.000 no mesmo algoritmo.

Isso não é um bug: protege contra olhar casual e contra dump acidental. Mas a interface oferece um toggle de "cifragem at-rest" que sugere uma garantia que o desenho não sustenta.

Correção: das duas, uma. Ou derivar a chave só de uma passphrase que nunca toca o storage (com o custo de UX de pedi-la a cada sessão), ou manter o modelo atual e ajustar o texto da interface para o que ele realmente entrega. Em qualquer caso, alinhar as iterações de PBKDF2 com o backend e cobrir todas as chaves com dado pessoal — hoje aprendizado_historico e o rascunho do formulário ficam de fora.
Como ficou: PBKDF2 alinhado ao backend (600k) via formato enc3, com leitura retrocompatível de enc2 e enc1 coberta por teste. O texto da interface passou a dizer de onde vem a chave. A limitação de fundo — sem passphrase, a chave mora no mesmo storage — permanece por decisão: resolvê-la exige pedir senha a cada sessão, e isso é escolha de produto, não de código.

P2 · resolvidoCSP libera o jsDelivr inteiro em script-src

index.html · dist/index.html

script-src 'self' https://cdn.jsdelivr.net https://cdn.belvo.com. O jsDelivr serve qualquer versão de qualquer pacote do npm — permitir o host é permitir código arbitrário de terceiros. Como o build já empacota tudo localmente (o lucide virou um subset de 27 KB em js/vendor.bundle.js), nada carregado hoje precisa desse host. Há também style-src 'unsafe-inline'.

Correção: remover cdn.jsdelivr.net de script-src e connect-src no harden-csp.cjs e verificar o boot com o smoke E2E, que já falha em qualquer pageerror. Depois, atacar o 'unsafe-inline' de estilo migrando os style="" restantes para classes.
Como ficou: Restringido a /npm/tesseract.js@5/ e /npm/tesseract.js-core@5/. O SRI com versão fixada ficou documentado em comentário, com o hash já calculado — não liguei porque o sandbox da auditoria não alcança o CDN e eu não conseguiria testar o OCR de ponta a ponta.

P2 · resolvidoLimite mensal do plano FREE conta pela data digitada

backend/middleware/plan.js — checkTransactionLimit

A contagem usa where: { userId, date: { gte: inícioDoMês } }. date é a data informada pelo usuário, não a de criação. Um usuário no plano FREE que lance com data retroativa nunca encosta no teto de 100/mês. Há ainda uma corrida clássica: contar e depois criar não é atômico, então requisições concorrentes ultrapassam qualquer limite.

Correção: contar por createdAt (é isso que o limite comercial quer dizer) e mover a checagem para dentro da mesma transação da criação, ou usar um contador incremental em UsageRecord — modelo que já existe no schema.
Como ficou: Passou a contar por createdAt, descartando tombstones. Quatro testes cobrem o caso, e os três que importam falham contra o código antigo. A corrida entre contar e inserir continua aberta, documentada no próprio middleware: fechá-la atravessa três camadas no caminho mais sensível do sistema, e o excedente é da ordem de unidades.

P2 · resolvidoO container não recebe o sinal de encerramento

Dockerfile — CMD

backend/server.js implementa shutdown gracioso caprichado: fecha o servidor, para os workers, drena as filas, desconecta Redis e Prisma, com timeout de 10 s. Só que o CMD ["sh", "-c", "npx prisma migrate deploy && node backend/server.js"] deixa o sh como PID 1, e ele não repassa SIGTERM. Na prática o Node é morto de supetão a cada deploy e todo esse cuidado nunca roda.

Correção: CMD ["sh","-c","npx prisma migrate deploy && exec node backend/server.js"] — o exec substitui o shell pelo Node, que passa a ser PID 1. Aproveite para acrescentar um HEALTHCHECK apontando para /health, que já existe e é completo. E rodar migrate deploy no start de cada réplica é uma corrida esperando acontecer: separe num job de release.
Como ficou: exec node backend/server.js no CMD, mais um HEALTHCHECK apontando para /health. Rodar migrate deploy no start de cada réplica continua em aberto — separar num job de release é decisão de infraestrutura.

P2 · resolvidoEm desenvolvimento, o servidor expõe a raiz do projeto

backend/app.js — resolveStaticRoot()

Fora de produção, STATIC_ROOT é a raiz do repositório, e express.static serve tudo que houver ali — incluindo .env (3,7 KB de segredos reais), backend/, prisma/ e o financaspro-upload.jks. O caminho de produção está corretamente fechado (falha se faltar o build), mas um npm run backend:dev em rede compartilhada, num café ou num túnel de preview, entrega a chave de assinatura do app da Play Store para quem pedir.

Correção: em dev, servir uma lista explícita (js/, css/, icons/, fonts/, index.html, manifest.json) em vez da raiz inteira, e vincular o listener a 127.0.0.1 quando não for produção.
Como ficou: Allowlist explícita de pastas e arquivos em modo dev; express.static na raiz só em produção, onde a raiz é dist/. Seis testes verificam que .env, package.json, backend/, prisma/, scripts/ e o .jks não saem mais — e quatro deles falham contra o código antigo.

É exatamente onde mora o fluxo que o usuário toca: preencher o lançamento, filtrar o extrato, editar a configuração. Prioridade 3 — dívida a agendar

P3Duas camadas de estado concorrentes no frontend

js/core/dados.js (1.141 LOC) · js/core/store.js (603 LOC)

O STORE se declara "fonte única de verdade", mas o próprio comentário do arquivo admite que transações, contas e config não moram nele — ficam no DADOS, e o store guarda só contadores de versão. Módulos como init-config, billing, pin e contas falam direto com o DADOS. Funciona, e é a origem dos 112 avisos no-undef e dos 44 globais.

P3Limites de plano em duas fontes de verdade

backend/middleware/plan.js · backend/prisma/seed-plans.js

PLAN_LIMITS está fixo no middleware e semeado no banco — o próprio comentário "(0 no seed = ilimitado)" denuncia a divergência de convenção entre os dois. Mudar o plano comercial exige lembrar de dois lugares que usam representações diferentes de "ilimitado".

Correção: o banco é a fonte, o middleware lê e cacheia com TTL curto. Isso resolve de quebra as 1–2 queries por requisição do getUserPlanTier.

P3Autenticação faz um SELECT por requisição

backend/middleware/auth.js

Todo request autenticado faz prisma.user.findUnique para hidratar req.user. É correto e seguro — pega desativação de conta na hora — mas soma com a consulta de plano: 2 a 3 queries antes de o handler começar. Não é problema hoje; vira um quando o tráfego crescer.

Correção: cache curto (30–60 s) do usuário em Redis, invalidado no logout e na desativação. Já existe Redis na stack.

P3Detalhes menores, agrupados

vários

  • npm run build reescreve sw.js na raiz do projeto, não só em dist/ — todo build suja a árvore de trabalho.
  • deploy.yml constrói a imagem com push: false. Não existe CD; o workflow só valida que o Dockerfile compila.
  • production-guard rejeita os segredos de dev por nome, mas aceita JWT_ACCESS_SECRET=abc. Falta um piso de entropia (≥ 32 caracteres).
  • O rate limiter cai para memória quando o Redis falha, em silêncio. Com múltiplas réplicas isso multiplica o limite pelo número de instâncias — vale uma métrica e um alerta.
  • field-crypto.js deriva a chave com SHA-256 puro, sem KDF nem versão de chave; rotacionar exige migração manual.
  • Assets com hash no nome são servidos com maxAge: '1h'. Podem ser immutable por um ano — index.html é o único que precisa revalidar.
  • Em todo boot sem backend o app chama /api/v1/state e registra um 404 no console. Ruído que mascara erro de verdade.

O que decidi não fazer, e por quê

  • SRI na tag do tesseract.js. Calculei o hash da versão que @5 resolve hoje (5.1.1) e deixei em comentário no index.html. Não liguei porque o sandbox da auditoria não alcança o jsDelivr: eu estaria entregando uma mudança que não consegui testar, num caminho sem cobertura. Fica para quem puder abrir o OCR uma vez.
  • Atomicidade no limite de transações. A corrida entre contar e inserir é real, mas fechá-la exige levar a contagem para dentro da transação de criação, atravessando rota, serviço e repositório — no caminho mais sensível do sistema, com um duplo de Prisma que declara "sem atomicidade real" e portanto não provaria nada. O excedente é de unidades e o efeito é comercial. Documentei no próprio middleware em vez de fingir que resolvi.
  • Tokenizar o CSS novo de auth.css e ux-polish.css. São arquivos da frente que estava em andamento no seu disco. O teto ficou em 352 com nota registrada no .css-debt.json explicando que 6 dos literais vieram de lá, não da auditoria.
  • Commitar qualquer coisa no git. Os arquivos estão no disco, não no índice. O repositório tem 254 alterações pendentes de duas frentes de trabalho, e escolher como fatiar isso em commits é decisão sua.

Estado do ambiente

As dependências já estão instaladas. O compression que o backend/app.js passou a importar foi instalado no seu node_modules, junto com o brace-expansion@5.0.9 que zera o npm audit. 5Método

Tudo que está neste relatório foi executado, não inferido.

  • Leitura de código: 94 arquivos JS de frontend (25.086 LOC), 80 de backend (6.983 LOC), 14.356 linhas de CSS, schema Prisma com 20 modelos e 38 índices, 7 migrações.
  • Testes: jest com cobertura nas duas suítes — 76 + 22 arquivos, 1.632 testes, 0 falhas. Playwright com Chromium real em 12 cenários E2E, incluindo axe-core.
  • Análise estática: ESLint em js/ e backend/, check-xss-sinks, check-contrast, check-css-tokens, check-bundle-budget, check-dist-orphans, sync-conflict-test, npm audit.
  • Build: npm run build completo — Vite, subset do Lucide, bundling, cópia estática, hardening de CSP, verificação de órfãos.
  • Performance: Chromium via CDP com Emulation.setCPUThrottlingRate: 4 e rede a ~1,6 Mbps / 150 ms de latência. Duas medições comparáveis: o dist/ como é servido hoje, e o mesmo dist/ atrás de compression().
  • Verificação pontual: UTILS.parseMoeda, UTILS.dividirEmParcelas e a soma em centavos executados em VM isolada para confirmar as correções da auditoria anterior.

Verificação das correções: cada mudança foi aplicada numa cópia isolada, com a suíte completa, o build, os nove passos da esteira e os 13 cenários E2E rodando a cada bloco. Onde a correção tinha teste, provei que ele falha contra o código antigo antes de considerá-lo válido — quatro testes da raiz estática e três do limite de plano ficam vermelhos no código anterior. A medição de performance foi refeita no build final. Só depois disso os 29 arquivos foram gravados no disco, com verificação de hash antes e depois e preservação das quebras de linha originais de cada arquivo.

Na fase de auditoria, nenhum arquivo do projeto foi modificado. Os testes de backend-smoke, backend-api e a suíte de integração não puderam rodar no ambiente da auditoria porque o prisma generate exige baixar os engines, e a rede estava bloqueada — no CI eles rodam normalmente.
