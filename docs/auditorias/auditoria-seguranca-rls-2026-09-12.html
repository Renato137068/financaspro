A modelagem é defesa em profundidade e está acima da média: RLS habilitada em todas as tabelas (negado por padrão), padrão de acesso "dono OU membro da org" com funções auxiliares SECURITY DEFINER de search_path fixo, billing/auditoria em deny-all (só o service_role escreve), e uma camada de 2FA/AAL2 bem construída (códigos de recuperação só em hash, políticas restrictive de segundo fator).

01

Escopo e método

Auditoria estática do código de segurança no repositório, cruzando o schema com as políticas e os testes.

  • Políticas RLS — supabase/migrations/20260828120000_rls_policies.sql e 14 migrations subsequentes (quota, AAL2, MFA, exclusão de conta, welcome-trial).
  • Schema — prisma/schema.prisma (20 modelos) + 4 tabelas criadas fora do Prisma nas migrations.
  • Testes — suíte pgTAP em supabase/tests/ (cobertura de RLS, AAL2, MFA, quota, convites).
  • Fora do escopo — cobrança (Edge Functions Stripe/Play, webhooks, secrets) e a verificação de que o projeto ao vivo tem todas as migrations aplicadas (ver seção 06).
02

Cobertura — toda tabela sob RLS

As 24 tabelas de public têm RLS habilitada. As que guardam dado sensível de billing/auditoria ficam em deny-all: RLS ligada e sem policy = nenhum cliente acessa; só as Edge Functions (service_role, que ignora RLS) escrevem.

03

Modelo de acesso

"Dono OU membro da org", implementado com funções auxiliares seguras.

  • IDs comparados corretamente — "userId" = auth.uid()::text (os IDs do Prisma são TEXT; comparar com o uuid cru falharia silenciosamente).
  • Funções SECURITY DEFINER (is_org_member/editor/admin) leem a filiação sem disparar a RLS da própria tabela — evitam recursão — e fixam search_path (barram injeção por search_path).
  • Papéis respeitados — VIEWER só lê; escrita exige OWNER/ADMIN/MEMBER. Convite visível para o admin da org ou para o e-mail convidado (via auth.jwt()).
  • Criação de User só por trigger — sem insert/delete pelo cliente; a linha nasce do trigger de auth e a exclusão passa por Edge Function (LGPD/Play).
04

Autenticação e 2FA

A camada de segundo fator é o ponto mais bem trabalhado da auditoria.

  • Códigos de recuperação só em hash — SHA-256 com o userId no hash (dois usuários com o mesmo código não colidem; vazar a tabela não permite comparar hashes entre contas), 64 bits de entropia, uso único, e os demais são invalidados junto.
  • Tabela de recovery blindada — deny-all + revoke all from anon, authenticated; todo acesso passa por funções SECURITY DEFINER que gatam o nível (gerar exige AAL2; consumir funciona em AAL1 — é justamente quem perdeu o autenticador).
  • Enforcement de AAL2 — políticas RESTRICTIVE _require_aal2 em 14 tabelas de dado do usuário: se a conta tem 2FA, uma sessão só-senha (AAL1) não enxerga os dados até completar o segundo fator. Restrictive soma com as permissivas — não há como "passar por cima".
  • Rate-limit de MFA e enforcement de quota por plano, ambos com tabela própria sob RLS.

Opcional 1 · clareza

WITH CHECK implícito nos UPDATE financeiros

As policies de UPDATE de Transaction/Account/Budget/RecurringTransaction definem só USING. É seguro — o Postgres reaplica o USING como check no UPDATE — mas um WITH CHECK explícito deixa a intenção evidente e protege contra um refactor futuro do USING mudar a semântica sem querer.

Nuance: como o USING inclui o ramo "org editor", um editor da org pode reatribuir o userId de um registro para outro membro da mesma org. É colaborativo por design — só vale estar ciente.
Opcional 2 · cuidado

Least-privilege nas funções auxiliares — não fazer do jeito ingênuo

As funções is_org_member/editor/admin têm EXECUTE para public (padrão). Revogar de anon parece "endurecer", mas quebraria o caminho não-logado: as policies base valem para public, então uma consulta anon avalia a função e passaria a receber erro de permissão em vez de "0 linhas". O jeito correto — restringir as policies a TO authenticated — é uma mudança maior que precisa do pgTAP rodando para validar. Recomendação: só encostar nisso depois da seção 06.

Nota · produto

AuditLog é deny-all ao cliente

Correto do ponto de vista de segurança. Se um dia você quiser que o usuário veja o próprio histórico de auditoria, será preciso adicionar uma policy de self-read ("userId" = auth.uid()::text). Decisão de produto, não pendência.

06

A verificação que falta (você roda)

Esta auditoria é do código. Se o seu projeto ao vivo tem todas as migrations aplicadas, não dá para ver daqui — o diagnóstico já mostrou RLS em User = sim, o que é um forte indício de que a rls_policies.sql rodou.

⚙ Rode a suíte pgTAP contra o seu projeto

É a checagem autoritativa: valida cobertura de RLS, AAL2, MFA e quota de ponta a ponta.

node scripts/test-supabase-pgtap.cjs      # ou: supabase test db

Passou = tudo aplicado e verificado. Falhou = a saída aponta qual migration falta.
