Achados priorizados

Sev.#Achado & correção
CORRIGIDOH1 Service worker guardava respostas REST do Supabase (dados financeiros) em texto puro no Cache Storage. Em sw.js, todo GET cross-origin com resposta ok era gravado no cache. As consultas de sincronização são GET PostgREST — SB.from('Transaction').select('*') etc. (supabase-sync.js:114-119). Consequências: (a) transações, contas e orçamentos ficavam não cifrados no cache, fora do escopo do LOCAL_CRYPTO (que só cobre chaves fp- do localStorage); (b) a chave de cache é a URL, idêntica entre usuários — num aparelho compartilhado e offline, caches.match podia servir os dados de um usuário para outro.

✓ Corrigido em 03/09/2026. A origem do Supabase (e todo cross-origin fora de uma allowlist explícita CACHEABLE_CROSS_ORIGIN) passou a ser network-only — só asset estático imutável de CDN (cdn.jsdelivr.net) é cacheável. O sufixo do cache foi bumpado -p2 → -p3, então o handler de activate purga automaticamente qualquer cache antigo já envenenado. Editado na fonte (scripts/generate-sw-cache.cjs) e regenerado em sw.js/dist/sw.js. Teste auth-sw-native.test.js reescrito para afirmar que a allowlist não contém o Supabase — 22 passed. Limpeza de cache no logout tornou-se desnecessária: dado do usuário não é mais cacheado.

MÉDIAM1 Consumo de código de recuperação do 2FA sem rate-limit / lockout. fp_mfa_recovery_consume roda em AAL1 (correto — é para quem perdeu o autenticador) e, ao acertar, remove o fator TOTP (20260903090000_mfa_recovery_codes.sql:104-140). Não há contador de tentativas nem bloqueio. Um atacante que já tenha a senha (sessão AAL1) poderia tentar força bruta para derrubar o 2FA. Mitigado na prática por 64 bits de entropia por código, mas o caminho não tem freio.
  • Adicionar contador de falhas por usuário + backoff (tabela ou coluna), espelhando o lockout do PIN.
  • Registrar cada consumo/tentativa no AuditLog.
MÉDIAM2 CSP confia em origens de script de terceiros e usa style-src 'unsafe-inline'. script-src inclui cdn.jsdelivr.net (Tesseract/OCR) numa página que guarda token de sessão — cada origem de script é confiança de execução de código. O harden-csp.cjs já remove Belvo e origens de dev no build, o que é ótimo, mas a CDN do OCR permanece.
  • Servir o Tesseract localmente — já existe js/vendor/tesseract.min.js; concluir a migração e remover jsdelivr do script-src/worker-src.
  • Migrar estilos inline para classes e remover 'unsafe-inline' de style-src (ou usar nonce/hash).
CORRIGIDOM3 Não havia garantia automática de que toda tabela nova nascesse com RLS. O modelo inteiro depende de RLS, mas 20260828120000_rls_policies.sql habilita RLS numa lista explícita de tabelas. Como o schema é do Prisma, uma tabela futura fora dessa lista ficaria sem RLS — legível/gravável pela anon key. Não existia teste/guard que falhasse o CI nesse caso.

✓ Corrigido em 03/09/2026. Criado supabase/tests/rls_coverage.test.sql (pgTAP): falha o CI se qualquer tabela base de public estiver sem RLS, salvo allowlist explícita (_prisma_migrations); tabelas de extensão são excluídas via pg_depend. Auto-descoberto pelo runner de pgTAP.

⚠ O guard já pegou um buraco real. A tabela fp_plan_limit_config (limites de plano, criada em 20260901150000) tinha nascido sem RLS. No Supabase isso a deixava gravável por authenticated via PostgREST — um usuário FREE poderia rodar update … set max_trans_per_month = null e furar a própria quota (os triggers leem os limites dessa tabela). Fechado em 20260903120000_fp_plan_limit_config_rls.sql: RLS ligada + SELECT público, sem escrita pelo cliente (mesmo padrão de Plan). Severidade real do buraco: MÉDIA→ALTA (bypass de monetização, não vazamento de dado alheio).

BAIXAL1 Segredo do RTDN do Play viaja em query string. play-rtdn/index.ts:41 aceita ?secret= (além do header x-rtdn-secret). Query strings vazam em logs de proxy/servidor. → Preferir exclusivamente o header e documentar o Pub/Sub para enviá-lo.
BAIXAL2 Backend Express legado permanece no repo com segredos de dev de fallback. backend/config.js tem 'dev-access-secret' etc. (protegidos por isProd, e o backend não é implantado). Código morto que manipula segredos é risco de deploy acidental. → Isolar em pasta claramente arquivada ou remover.
BAIXAL3 Cifragem local no modo "dispositivo" guarda a chave junto do dado. local-crypto.js deriva de financaspro_ckey_dev no mesmo localStorage — não protege contra XSS nem perícia. O código já documenta isso honestamente e a UI avisa; fica como nota. → Incentivar o modo passphrase para quem quer proteção real at-rest.

O que está bem-feito (e é raro ver)

🛡️ Banco de dados — o ponto mais forte

  • RLS negado por padrão, padrão "dono OU membro da org" consistente em todas as tabelas de dados.
  • Todas as funções auxiliares são SECURITY DEFINER com search_path fixo — fecha o vetor clássico de sequestro de search_path.
  • Tabelas internas (AuditLog, Session, VerificationToken, webhooks) com RLS ligada e sem policy = deny-all; só o service_role escreve.
  • Quota do plano FREE imposta por trigger no Postgres (não só no app), espelhando plan-limits.json com teste de paridade.
  • Exclusão de conta pelo próprio usuário (fp_delete_own_account) para LGPD/Play, com grant só para authenticated.

🔐 2FA imposto no banco, não só na tela

A migration require_aal2 resolve o erro que quase todo app comete: signInWithPassword devolve sessão AAL1 válida mesmo com TOTP ativo. Uma policy RESTRICTIVE combinada por AND (fp_mfa_ok()) nega leitura/escrita a sessões AAL1 quando a conta tem fator verificado. Isso torna o 2FA real contra quem fala direto com o PostgREST.

💳 Webhooks e billing

  • Stripe: assinatura verificada com constructEventAsync (Web Crypto) antes de processar.
  • Play RTDN: segredo compartilhado + reverificação server-to-server na Google Play API (não confia no payload do push).
  • Idempotência por event.id/messageId com claim/release; escrita de billing só via service_role.

🔑 Autenticação, PIN e segredos

  • Anti-enumeração de usuários em cadastro e login (mesma resposta para e-mail novo e repetido).
  • Troca de senha expulsa as outras sessões (signOut scope:'others').
  • PIN: PBKDF2-SHA256 310k, salt por usuário, comparação tempo-constante, recusa de PINs fracos, backoff exponencial — e a UI é honesta sobre ser "tranca de conveniência".
  • Nenhum service_role/sk_live/chave privada commitada; anon key é pública por design (segurança fica na RLS); .env e keystores no .gitignore.
  • Refresh token biométrico no Android Keystore; rotação de token tratada.

📱 Android & web

  • allowBackup="false" (bloqueia backup adb dos dados locais), FileProvider não exportado, só permissão INTERNET, sem cleartext.
  • CSP com object-src 'none', base-uri 'self', form-action 'self', sem 'unsafe-eval' em script; nosniff + Referrer-Policy.
  • Saída de texto do usuário (descrição, categoria, nome de banco) escapada com UTILS.escapeHtml de forma consistente.
  • Cobertura de testes de segurança: pgTAP para RLS/MFA/quota + testes JS de CSP, política de senha e estáticos de segurança.
