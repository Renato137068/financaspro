Regular — bom motor, com 1 bloqueador crítico de release A engenharia por trás do Resumo é sólida (renderização modular, cache, dados em centavos). Mas a peça mais importante da tela — o saldo do mês — está renderizada em branco sobre fundo quase branco no tema claro (padrão), com contraste de 1,05:1. Corrigido esse defeito, a aba salta para a faixa de 80+.

! Achado crítico (bloqueador)

Verificado no navegador com o app rodando (getComputedStyle + cálculo WCAG), tema claro padrão.

P0 · Bloqueador

O saldo do mês é texto branco sobre fundo quase branco — invisível no tema claro

O elemento herói do dashboard (#card-saldo-principal .saldo-valor) recebe color: var(--color-white) (#fff). O cartão perdeu seu fundo colorido decorativo (comentário “Removidos efeitos decorativos para seguir padrão limpo” em css/layouts/dashboard.css:55), mas as cores de frente continuaram brancas. O fundo efetivamente pintado atrás do número é o body = #f6fbf8. Resultado: o valor, o rótulo (“Saldo do mês”) e o ícone de tendência ficam ilegíveis.

Cor do texto (saldo) rgb(255, 255, 255)
Fundo efetivo (body) rgb(246, 251, 248)
Contraste medido 1,05 : 1  →  reprova WCAG (mín. 3:1 texto grande, 4,5:1 normal)
Tema escuro 15,08 : 1  →  OK (o override de dark-mode salva o dark)

Causa-raiz — duplicação de CSS. As regras do cartão de saldo estão repetidas em três arquivos (css/components/cards.css:113-131, css/layouts/dashboard.css:120-126 e css/features/superficie.css:106-121). O fundo foi alterado num arquivo e a cor do texto ficou nos outros — clássica regressão de fonte-única quebrada.

Correção sugerida. Como o cartão agora é uma superfície clara, a frente deve ser escura no tema claro e branca só no escuro. Consolidar em um arquivo:

  • .card-saldo-principal .saldo-valor { color: var(--color-text-primary); }
  • .card-saldo-principal .saldo-label { color: var(--color-text-muted); }
  • ícone do .saldo-emoji → color: var(--color-primary-text) (hoje branco sobre tint claro).
  • manter o branco apenas sob [data-theme="dark"], onde o fundo do cartão é escuro.
  • remover as duas cópias redundantes das regras .saldo-valor/.saldo-label.

Teste de regressão. Nenhum teste atual mede contraste computado — por isso passou despercebido. Adicionar uma verificação (mesmo o snippet de contraste usado nesta auditoria) ao tests/a11y-static.test.js impede a reincidência.

3 Roadmap de melhorias

Priorizado por impacto × esforço. P0 sai antes de qualquer publicação; P1 é a próxima sprint; P2 é polimento contínuo.

P0 · agora Restaurar a legibilidade do herói

Meta: o número mais importante da tela precisa ser lido em ambos os temas. Bloqueia release.

Corrigir cor branca do saldo no tema claro~30 min · trivial

Trocar --color-white por --color-text-primary/muted nas regras do cartão claro; manter branco só no dark. css/features/superficie.css:106, css/components/cards.css:122, css/layouts/dashboard.css:120.

Consolidar as 3 cópias das regras do cartão de saldo~1 h · baixo

Uma única fonte de verdade (preferir components/cards.css) elimina a classe de bug que causou o P0.

Teste de contraste automatizado~1 h · baixo

Adicionar cálculo de razão de contraste dos elementos-chave do Resumo ao tests/a11y-static.test.js. Falha se < 4,5:1.

P1 · próxima sprint Acessibilidade & foco na informação

Meta: o Resumo volta a resumir, e o leitor de tela recebe a informação sem ruído.

Reduzir o re-anúncio do role="status"~2 h · médio

O cartão de saldo (index.html:186) é role="status" e é reescrito a cada mudança de dados (subscribe dados → re-render). O leitor de tela relê o saldo inteiro a cada lançamento. Anunciar só quando o valor mudar de fato, ou mover o aria-live para um resumo textual curto.

Alternativa textual para os gráficos SVG~3 h · médio

BarChart6M e DonutChart expõem role="img" + aria-label genérico, mas os dados (valores por mês/categoria) não são acessíveis. Adicionar uma tabela .sr-only ou aria-label com os números.

Domar a densidade da aba~1 dia · médio

A aba empilha 14+ seções (saldo, cards, indicadores, insights, previsão, disponível, cartões, contas, contas a pagar, relatório, gráficos, orçamento, metas, assinaturas, patrimônio, últimas transações). Um “resumo” que mostra tudo deixa de resumir. Priorizar 4–5 blocos acima da dobra e colapsar o resto por padrão.

P2 · contínuo Performance, robustez e consistência

Meta: manter o Resumo rápido e correto à medida que o app cresce.

Memoizar obterResumoMes entre sub-renderers~3 h · médio

renderChartEvolucao recomputa 6 meses de resumo a cada render; comparação e indicadores repetem cálculos do mês. Cachear por (mês,ano) enquanto os dados não mudam.

Chamar renderLucideIcons uma vez por render~1 h · baixo

Vários sub-renderers chamam renderLucideIcons individualmente e ainda há um renderLucideIconsNow no fim de render() — varreduras de DOM redundantes.

Erros silenciosos observáveis~2 h · baixo

Cada sub-renderer engole exceções com console.error (bom para não quebrar a tela), mas uma seção que falha some sem sinal. Encaminhar para a telemetria já existente (observability.js) e mostrar um estado de erro discreto.

Rever o indicador “Economia prevista”~1 h · baixo

render-dashboard.js:302 usa renda − despesas (renda configurada), ignorando as receitas reais lançadas no mês. Para quem tem renda variável, o número engana. Considerar receitas − despesas ou rotular claramente a base.

Reduzir acoplamento do render()~meio dia · médio

O renderer do dashboard chama diretamente INIT_METAS, INIT_CONTAS_PAGAR, INIT_ASSINATURAS, INIT_PATRIMONIO, INIT_RELATORIOS. Inverter para registro/eventos (cada módulo se inscreve no render do dashboard) melhora testabilidade e isolamento.

4 O que já está bom (manter)

  • Dados em centavos inteiros nos dois caminhos (service e fallback) — evita drift de arredondamento no total do mês (transacoes.js:255-266).
  • Transferências excluídas das despesas por comparação explícita, não else — o total do mês não infla (transacoes.js:257-260).
  • Renderização modular com cache de DOM/dados, batching por requestAnimationFrame e DocumentFragment (render-core.js, render-dashboard.js).
  • Lazy render dos gráficos — só renderiza quando o painel “Análise detalhada” está visível.
  • Defensividade — cada sub-renderer é isolado em try/catch; uma seção quebrada não derruba a aba.
  • Segurança de DOM — uso predominante de createElement/textContent; innerHTML restrito a SVG/valores numéricos.
  • Dark mode dos gráficos — dark-mode.css sobrescreve fill/stroke dos textos e linhas dos SVGs.
  • Empty states dedicados para cada bloco sem dados, com CTA para a ação correta.

5 Metodologia & conceitos aplicados

Auditoria combinando análise estática do código com medição em runtime no app rodando localmente.

  • Acessibilidade: WCAG 2.1 (contraste 1.4.3, alternativas não-textuais 1.1.1, regiões live 4.1.3), semântica ARIA.
  • Contraste medido: getComputedStyle + luminância relativa/razão de contraste calculadas sobre o fundo efetivo (herança de background).
  • Arquitetura: acoplamento/coesão, fonte-única de verdade, separação render/dados.
  • Performance de render: recomputação redundante, varreduras de DOM, lazy rendering, batching.
  • Correção financeira: aritmética em centavos, classificação de tipos, paridade entre caminhos de cálculo.
  • Manutenibilidade: duplicação de CSS, cascata/especificidade, tokens de design.
  • UX / arquitetura da informação: hierarquia visual, densidade, “above the fold”.
  • Segurança de front-end: superfície de XSS via innerHTML.
  • Testabilidade: cobertura de regressão para os defeitos encontrados.

Escopo estritamente limitado à aba Resumo e aos componentes que ela renderiza (render-dashboard.js e components/ associados). Backend, sync e demais abas ficaram de fora por definição do escopo.
