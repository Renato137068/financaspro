Sumário executivo

O FinançasPro é um SaaS financeiro completo: PWA offline-first, Android via Capacitor, backend Express/Prisma com billing Stripe, Open Finance (Belvo), 2FA TOTP, organizações multi-tenant, workers BullMQ e retenção de dados. A engenharia de plataforma está acima da média. A camada de dinheiro — que antes tinha bugs silenciosos — foi corrigida nas Fases 1–10. O app responde perguntas críticas como saldo por conta, comprometido, fatura de cartão e projeção de fim de mês.

Pontos fortes

Produto e finanças

  • Cartões de crédito completos — ciclo de fatura, limite, confirmação de pagamento (Fase 5–6).
  • Dashboard orientado a decisão — saldo, comprometido, disponível para gastar, metas com projeção.
  • Orçamento em centavos — melhor módulo; testes provam que 1.000 × R$ 0,10 = R$ 100,00 exatos.
  • Entrada rápida restaurada — #entrada-rapida-input e .er-wrapper presentes no HTML.
  • Open Finance — Belvo + sandbox, deduplicação por openFinanceId, widget CSP-safe.

Engenharia

  • 1.548 testes — 71 suítes frontend + 13 backend, ~12 s cada lado.
  • Guardrails automatizados — XSS, contraste WCAG, CSS tokens, bundle budget, dist orphans.
  • Build limpo — Fase 10 removeu 1,29 MB de artefatos órfãos por build.
  • Zero catch vazio — Fase 8 substituiu por UTILS.tentar com OBS + feedback.

Segurança

  • CSRF guard verifica Origin/Referer para cookies de sessão.
  • Refresh token armazenado como hash; rotação de sessão no logout.
  • 2FA TOTP real (otplib), lockout por e-mail, RBAC por organização.
  • CSP hardened em produção (harden-csp.cjs remove localhost).
  • Retenção de dados com worker dedicado e política documentada.

Infraestrutura

  • CI com matriz Node 18/20, Postgres 16, Playwright no Node 20.
  • Fontes auto-hospedadas — offline-first sem depender do Google Fonts.
  • Lucide subset: 130 ícones → 27 KB (era ~390 KB).
  • Capacitor 8.4 para Android/iOS com scripts de release.

Riscos e gaps

Ordenados por impacto no release e confiança do usuário.

P0

E2E vermelho — dashboard não hidrata no Playwright

10 specs falharam aguardando #card-saldo-principal conter "R$". A navegação carrega (mudarAba existe), mas RENDER_CORE.renderAll() não popula o card de saldo. Receitas/despesas permanecem no default HTML (R$ 0,00).

Evidência: npx playwright test em 22/08/2026; timeout em e2e/app.offline.spec.cjs:51.

P1

Frontend ainda depende de bundle concatenado e globais

app.bundle.js (435 KB) concatena 82 scripts. 180 warnings ESLint (majoritariamente no-undef entre módulos). Ordem implícita dificulta manutenção e onboarding de contribuidores.

Risco: regressões difíceis de isolar; cada feature nova aumenta o acoplamento.

P1

Code splitting limitado

Lazy load cobre apenas previsao, relatorios e conta. Billing, 2FA, Open Finance, OCR e patrimônio carregam sempre no bundle principal.

Precache total: 955 KB (87% do teto de 1.100 KB).

P1

3 vulnerabilidades high no npm audit

js-yaml (CVE-2026-59870) e nanoid (GHSA-2v37-7h3g-55p8) em dependências de dev. Corrigível com npm audit fix.

P1

Duas camadas de estado (DADOS + STORE)

DADOS (961 LOC) persiste; STORE (574 LOC) é fonte em memória. Módulos usam camadas diferentes, aumentando risco de divergência.

P2

Dívida de CSS estável mas alta

348 valores literais fora do design system (229 cores hex + 119 font-size px). Teto registrado em 2026-08-10 — não cresce, mas não diminui.

Maior concentração: orcamento.css (75), ia.css (58).

P2

Arquivos init monolíticos

init-config.js (1.418 LOC), init-form.js (1.392 LOC), init-extrato.js (1.135 LOC) concentram lógica de UI difícil de testar isoladamente.

P2

Documentação de auditoria dispersa

13 arquivos HTML de auditoria com notas e datas diferentes. Risco de decisões baseadas em relatório desatualizado.

Roadmap sugerido

Sequência que minimiza retrabalho: primeiro provar o release (E2E), depois performance e arquitetura.

Sprint 0 — Desbloquear release

E2E verde e smoke de produção

  • Investigar por que RENDER_CORE.renderAll() não popula o dashboard no Playwright (possível race com lazy-load ou init order no bundle).
  • Atualizar fixture E2E para aguardar evento observável (data-dashboard-ready) em vez de polling de DOM.
  • Adicionar teste de smoke que carrega dist/?offline=1 e falha em qualquer pageerror.
  • Corrigir npm audit fix e validar que testes continuam verdes.
Sprint 1 — Performance perceptível

Bundle enxuto e carregamento progressivo

  • Lazy load para billing, 2FA, open-finance, OCR e patrimônio.
  • Medir LCP/INP/CLS com Lighthouse CI no pipeline.
  • Reduzir CSS de ia.css e orcamento.css (75 literals).
Sprint 2 — Arquitetura frontend

Reduzir fragilidade estrutural

  • Fragmentar os 3 arquivos init monolíticos.
  • Unificar DADOS + STORE com contrato explícito.
  • Atacar warnings ESLint por domínio (form, extrato, config).
  • Iniciar migração ES modules conforme ADR-0002 — uma feature por PR.
Sprint 3 — Release Play Store

Operação e distribuição

  • Gerar e testar AAB assinado em dispositivo real.
  • Validar permissões, splash, ícones e política de privacidade.
  • Runbook de rollback, backup e incidentes.
  • Publicar este relatório como fonte oficial de auditoria.
